### Tool layer
- `FNameTBDAITool` {Name, Description, InputSchema, bWrites, bInAskMode, bOptIn, Run}; `NameTBDAITools::Register / Execute`. `FNameTBDAISchema` builds the plain JSON-Schema subset every provider takes. `Execute` checks required fields and coerces what models get loose (numbers as strings, objects and lists as JSON text - needed for Gemini, whose schema subset can't hold free-form objects - single values for lists, enums matched loosely), refuses writes where they're off, and runs a write inside an `FScopedTransaction` (nested into the chat request's own open transaction when there is one).
- `FNameTBDAIToolResult` {bOk, Data (compact JSON), Error, Warnings, Images}; `ToText()` is what the model reads. `FNameTBDAIChangeSet` {CreatedAssets, TouchedPackages, Lines}: Discard deletes the created assets, Apply saves the packages, the lines fill the change card. `SetLastAsset / GetLastAsset`: "the one just made" - every tool that takes a blueprint / animation treats an omitted name as it (then the most recently used Widget Blueprint editor).
- **JSON <-> properties (`NameTBDAIJson`)** - what makes the tools generic: loose names (case / spaces / underscores / a bool's b / display names / a unique prefix or substring: "Typeface" -> TypefaceFontName; exact matches ranked whatever the field order - own name, then display name, then a bool without its b - so a shape's "Fill" is the Fill paint, not bFill whose display name is also Fill), paths as keys ("Fill.Color", "ValueKeys.Keys[1].Value", "LayoutData.Anchors"), "List+" appends (a list appends each item), colors "#RRGGBB[AA]" (sRGB) / [r,g,b,a] (linear) / names, numeric structs from arrays in field order ([x,y], margins [h,v]), FSlateColor, FSlateBrush from a texture/material path, enums by name / display name / the part after "_" (HAlign_Center = Center), classes by short name or Blueprint path, soft refs, instanced objects {"$class"}, instanced structs {"$type"} (BaseStruct respected), property bags by their fields, maps, else ImportText. ClampMin/Max honoured. `ApplyToObject` = Modify + PreEditChange + write + PostEditChangeProperty per top-level field, asset/class fields first (a Niagara System lays out User Parameters before they're written). Reading: `ReadObjectNonDefault` / `ReadNonDefault` - editable fields that differ from the class defaults / struct defaults, compact (colors as hex, vectors as arrays, at most 24 list items, 60 fields).
- **Theme**: `UNameTBDAITheme` (data asset; dark + light palettes, type scale, spacing scale, radii, button motion, entrance timing, spring preset, card size); `Get()` = the settings' Theme or the class defaults (dark violet/teal). **Theme tokens** in any value, expanded by every write tool: "@surface", "@text~0.6" (alpha x 0.6), "@space.4", "@radius.large", "@type.title", "@font.strong", "@spring.Bouncy" (a whole `FWidgetSpringParams` from the built-in / project spring presets).
- **Tools (37 - `validate_material` added in v2; the three menu tools with the menu system, see MenuSystem.md):**
  - Read (offered in Ask mode): `get_context` (open assets, focused Widget Blueprint, designer selection with settings, last built, Content Browser selection), `describe_widget_blueprint` (tree, optionally with settings), `describe_widget` (one widget + slot, or one field path), `list_options` (widget_classes, components, track_types, motion_recipes, spring_presets, track_presets, material_masters (v2: filter = one master with its graph), material_functions, material_nodes (v2: the catalog + macros; filter = one node in detail, "all" = every class), material_macros (v2), niagara_templates, theme, enum <name>, fields <class or struct>), `search_docs`, `get_docs`, `find_assets`, `get_asset`, `open_asset`.
  - Widgets: `create_widget_blueprint` (unique WBP_ name, root panel; `size` puts it in a Size Box "Frame" - children go into "Content"), `add_widgets` (a whole nested tree in one call: {class or role, name, text, button: ready-made kind, label, props, slot {align: top_left..bottom_right|fill, padding, ...}, children}), `set_widget` (props / slot / text / role), `remove_widgets`, `move_widget`, `set_shape_paint` (color, linear/radial gradient {stops [[pos, color]], angle, center, radius}, or a material; fill or stroke; a ready-made button's Background Look), `apply_theme` (repaints role colors in the other palette), `compile_and_save`.
  - Widget creation matches the designer: `ConstructWidget` in the Blueprint's tree, `InsertChildAt / AddChild`, `CreatedFromPalette()`, then every widget of the tree that has no GUID gets one (reflection on `WidgetVariableNameToGuidMap`, the GUID rule above - hidden button parts are skipped), `MarkBlueprintAsStructurallyModified`, compile (problems returned). Ready-made buttons are built at once (`ConsumePendingDefaultContent` + `BuildDefaultContentForEditor` + `SetPartsHidden` + `MarkPartsVisibilityDecided` - what `StyledButtonsEditor::BuildPendingInBlueprint` does), then Style (AccentColor @accent, the theme's Motion) and `SetLabel`. Removing renames the widget and everything inside it to the transient package and drops their GUIDs.
  - **Roles** (`Roles.json`): card, panel, pill, badge, divider, scrim, display, title, heading, body, caption, label, glow (radial gradient), aurora (bottom gradient rising, rounded to the card's bottom corners), particles (Niagara widget, bottom-center origin), icon, stack, row, frame; button, button_primary, button_ghost, icon_button, toolbar (see "Widgets that read well"). Which role each widget was built with is remembered in `Saved/NameTBDAI/roles.json` (for `apply_theme`, which only rewrites the role's color tokens).
  - Animation: `create_widget_animation` (WA_, optional tracks or a recipe), `add_tracks` ({type, target, group, start, name, stagger {"$type"}, fields}; a field the track lacks goes to TypeParams; "$Param" / "-$Param" binds), `set_track` (scalar fields through `SetTrackProperty`, which keeps every other track in place), `remove_tracks`, `set_animation_parameter`, `apply_track_preset`, `save_track_preset`, **`animate_widget`** (a recipe made into WA_<Blueprint>_<Widget>_<recipe> next to the Widget Blueprint, or an asset; a Widget Animation Component added to the widget if it has none; an Anim In / Anim Out entry: when on_construct / on_visible / loop (+ ping_pong, loop_count) / by_id (Anim ID) / out). Built on `UWidgetAnimScriptAnimation` (`EditAnimationAsset`); the asset is told afterwards as the scripting layer tells it (`SyncAllTransformAnims`, `AssignDefaultValueNames`, PostEditChangeProperty on Layers). **Motion recipes** (`Motions.json`, {placeholders} from params): fade_in, pop_in, bounce_in, slide_up_in, slide_in_left, slide_in_right, drop_in, pulse_loop, breathe_loop, float_loop, spin_loop, wiggle, shake. An Out entry plays its animation backwards, so exits use entrance recipes.

  - Content: `create_material_instance` (of a library master or any material; numbers -> scalars, colors -> vectors, paths -> textures, bools -> static switches), `set_material_parameters`, `validate_material` (v2: checks a graph, builds nothing), `build_ui_material` (a node graph -> a UI material - v2: checked and repaired first, not built while it has errors; `from_master` extends a master or, alone, makes an instance; compile errors mapped to node ids; rebuild in place with 'material'), `create_niagara_ui_system` (copy of a template, friendly params mapped to module constants and widget settings, returns the widget props to use), `set_niagara_parameters` (widget User Parameters / widget fields / the template's friendly params on the system asset).
  - Data: `set_component` (any UI component, added if missing), `add_trigger`, `add_list_binding`, `add_sample_set` (append to the Widget Data Binder's lists, binder added if missing), `create_asset` (data assets - state machines etc.), `set_asset` (any asset's fields by path).
  - Menus: `create_settings_menu` (a whole settings screen: `WBP_` Menu Settings Screen + a Settings Menu filling it + a `DA_..._Style` Menu Style it is bound to + a schema for tabs that aren't built-in), `add_menu_settings` (setting specs -> a Settings Schema, optionally listed in a menu), `list_menu_settings` (read: pages, setting ids, graphics features, style presets). Docs `menus.md`.
  - `capture_preview` (opt-in): the generated class instanced in the editor world, drawn with `FWidgetRenderer` for N frames (entrances done, particles flowing), read back, PNG (`FImageUtils::PNGCompressImageArray`), at most 1024 px a side; handed to the model as an image (Anthropic tool_result image block, OpenAI a following user message, Gemini inlineData, MCP image content).

### Library (masters, functions, Niagara templates)
- `NameTBDAILibrary`: each asset is looked for in the plugin's own content first (`/NameTBD/AI/Materials/M_UI_<Name>`, `MF_UI_<Name>`, `/NameTBD/AI/Niagara/NS_UI_<Name>` - where a release can ship them built), then in the project's Library Folder (default `/Game/NameTBD_AI/Library`), else built there from `Resources/AI` and saved. Builds run with `GUndo` nulled, so they are never part of a request's undo step.
- Graph format (shared with `build_ui_material`): {domain UI | Surface, blend Translucent | Additive | Masked | Opaque, nodes [{id, type (MaterialExpression class without the prefix, a catalog alias, or a macro), props, function (for MaterialFunctionCall), inputs {InputName: "node" | "node.Output" | number | [x,y(,z(,w))] | "#hex" | "$uv" | "$time" | {"param": Name, "value": v}}}], outputs {FinalColor, Opacity, OpacityMask}}; functions add inputs [{name, type Scalar/Vector2/Vector3..., preview}] and outputs {Name: ref}. Since v2 every graph (shipped or the model's) goes through `NameTBDAIMaterialGraph::Prepare` first, then `BuildPreparedMaterial` / `BuildFunctionGraph`: nodes made with `UMaterialEditingLibrary::CreateMaterialExpression(InFunction)`, wired by the engine's own pin / output indices (`FExpressionInput::Connect`, `UMaterial::GetExpressionInputForProperty`), laid out, recompiled; errors from `GetMaterialResource(GMaxRHIShaderPlatform)->FinishCompilation()` + `GetCompileErrors()` / `GetErrorExpressions()`.
- v2: a project's library copies (`M_UI_*` / `MF_UI_*` in the Library Folder) are stamped with their definition's MD5 in `Saved/NameTBDAI/library_versions.json` (a master's stamp includes every function's definition) and rebuilt in place when the definition changes - so libraries built by v1 (broken `ColorRamp`, see v2) heal themselves on first use. Shipped `/NameTBD/AI/...` assets are never touched.
- **Since `_v2_fix4` every master and function is written in HLSL** (`"hlsl"` in its definition instead of `"graph"`: a master = its params + one Custom node returning float4(color, alpha); a function = one Custom node per output) - see the fix4 change set. Masters: **Aurora** (bands rising from the bottom, three colors drifting by Speed, Height, Falloff, Intensity, Glow), **SoftGlow** (round, can breathe), **Shimmer** (sweeping band), **Gradient** (three colors at an angle, can drift), **NoiseFog**, **Vignette**, **RingPulse**, **Dissolve** (Progress), **SoftDot** and **Bubble** (particles). Functions: **SoftCircle**, **RoundedRectSDF**, **PanningNoise**, **ColorRamp**. Every master multiplies by Vertex Color (RGB and A), so widget tints and particle colors apply. Since `_v2_fix5` every Custom node (library or model-written) is linted and made portable, may call the `NTB_` helpers of `Shaders/NameTBDUI.ush`, shows its code in its comment bubble and is titled with the material's name; materials build with full precision for their expressions - see the fix5 change set.
- Niagara templates (RisingBubbles, Sparkles, Confetti, Embers, GlowRing, Trail, RisingSparkleLoop): a shipped `NS_UI_<Name>` is copied as it is. Without one, a template is made once: a base system copied (Sparkles: the plugin's own `/NameTBD/NS_UISparkle`), else a new system with the engine's emitter template (`/Niagara/DefaultAssets/Templates/Emitters/Fountain` etc.; `UNiagaraSystemFactoryNew` + `FNiagaraEditorUtilities::AddEmitterToSystem`, compiled in only if those headers exist), then made UI-ready (CPU, local space, a UI material - Bubble / SoftDot - on sprite renderers that don't have one) and tuned through **rapid-iteration constants** matched by the end of their names ("SpawnRate.SpawnRate", "GravityForce.Gravity", "AddVelocityInCone.VelocityStrength", "InitializeParticle.LifetimeMin"...; each reports set / not found). **This fallback is approximate** (a fountain made gentle, not a real bubble stack): each recipe's `intended_stack` says what the shipped asset should be. Which template a system came from: `Saved/NameTBDAI/niagara_systems.json`.

### Docs (local, free)

### MCP server
- `FNameTBDAIMcpServer`: Streamable HTTP, JSON-RPC 2.0 posted to `http://127.0.0.1:<McpPort, 47917>/mcp`, one JSON answer per POST (202 for notifications; GET 405; DELETE ok). The listener is asked to bind 127.0.0.1 (`HTTPServer.Listeners` `ListenerOverrides` for the port), non-loopback peers are refused (403), and every request needs `Authorization: Bearer <token>` (401) - the token kept in the per-user settings (`McpToken`, Regenerate Token). Route handler made for either form of `FHttpRequestHandler` (delegate or TFunction) with a C++20 `requires` check. Methods: initialize (protocol 2025-06-18 / 2025-03-26 / 2024-11-05; `instructions` = the map), ping, tools/list (write tools hidden when MCP Allow Writes is off; capture only when allowed; readOnlyHint annotations), tools/call (text + image content, isError; each call its own undo step; saved after with MCP Save After Writes), resources/list + read (`nametbd://map`, `nametbd://docs/<topic id>`), prompts/list + get (`Resources/AI/Prompts/*.md`: "# Title", "> description", "Arguments: name - what", text with {{name}}). Batches answered as arrays.
- Connection file `Saved/NameTBDAI/mcp.json` {port, token, project}, written on start. **Bridge** `Resources/AI/MCP/nametbd_mcp_bridge.py` (stdlib only, runs on the engine's own Python): stdin lines -> POST -> stdout lines, keeps Mcp-Session-Id, reads the file each request, answers JSON-RPC errors when the editor is off / the token is wrong. Tested here against a mock server.
- Settings buttons: **Copy Claude Code Command** (`claude mcp add --transport http nametbd http://127.0.0.1:<port>/mcp --header "Authorization: Bearer <token>"`), **Copy Claude Desktop Config** (mcpServers.nametbd = engine Python + bridge + --project), Start / Stop Server, Regenerate Token, Build Library Now.

### Chat
- **Providers** (`NameTBDAIProviders`), HTTP module only, streamed as server-sent events (`SetResponseBodyReceiveStreamDelegateV2` -> a locked byte buffer -> split into events on the game thread at 30 Hz), or whole (Stream Replies off). Each adapter keeps the conversation in its provider's own form and sends back what it must byte for byte.
  - **Anthropic** (Messages API): system = the map with a `cache_control` breakpoint (tools + system = cached prefix) + top-level automatic caching; tools with `eager_input_streaming` (input parsed strictly at block stop; invalid JSON -> the call isn't run, the model gets an INVALID_JSON error result); `output_config.effort` from the settings; no `thinking` sent (adaptive on current models); thinking blocks kept with their signatures and echoed unchanged (history append-only); on api.anthropic.com: `context_management` `clear_tool_uses_20250919` (beta `context-management-2025-06-27`) so old tool results are cleared by the API instead of edited by us, and `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`) for Opus 5 / 5.5, Sonnet 5.5 and Fable (Refusal Fallbacks setting). A `refusal` stop drops the partial reply; after a mid-reply fallback the blocks before the last fallback marker that the fallback model can't use are dropped as the API asks. Defaults: Generation `claude-opus-5-5` (effort medium), Question `claude-haiku-5-5` (effort low); prices built in (Opus 5.5 4 / 20 / cache read 0.2, Sonnet 5.5 2 / 10, Haiku 5.5 0.1 / 0.5, Opus 5, Fable 5.1).
  - **OpenAI** Chat Completions and **OpenAI-compatible** endpoints (Ollama, LM Studio...: base URL + /chat/completions, `max_tokens`, no stream_options): system message = the map; tool results older than Collapse Tool Results After user turns are sent shortened (built per request - stored history untouched); images as a following user message.
  - **Gemini** (`streamGenerateContent?alt=sse`, `x-goog-api-key`): systemInstruction, functionDeclarations (schema upper-cased, free-form objects as JSON text), every model part kept as it came (thought signatures), functionResponse with the call id when Gemini gives one.
  - Errors in words: key refused (401/403), model / endpoint not found, rate limit (429), provider trouble (5xx), "this model may not support tool calls".
- **Session** (`FNameTBDAIChatSession`, owned by the module): Build mode = the Generation model with every tool; Ask mode = the Question model with the read tools. A Build request opens `GEditor->BeginTransaction("NameTBD AI: <prompt>")` at its start and ends it when the model ends its turn (or on error / Stop) - **one undo step per request**. Then the **change card** (Confirm Changes on): Apply saves (Save On Apply); Discard undoes that step if it's still the last one (else explains; a request that only made assets just deletes them) and force-deletes the assets it created (their editors closed first). Starting another request applies an open card (iterating = keeping). Tool calls run one tick after the reply (the panel shows them first); Stop answers pending calls as cancelled so the next request is valid. Max Tool Calls Per Request (60) stops a runaway loop. Attach Selection adds get_context's output to the message. Cost per request and per chat from Model Prices.
- **Panel** (`SNameTBDAIChat`, nomad tab "NameTBD AI" in Window's Tools section): Build / Ask switch, provider - model, New Chat, settings gear; messages (code fences in mono, Copy on replies), tool lines (tooltip = result), change cards, errors; the reply streaming in; status ("Thinking", "Writing add_widgets", "Running add_widgets"); input (Enter sends, Shift+Enter new line), Send / Stop; Attach selection; tokens (cached) and cost. Example prompts on an empty chat (the acceptance test first).
- **Settings** (`UNameTBDAISettings`, Editor Preferences > Plugins > NameTBD AI, `EditorPerProjectUserSettings` - never Default*.ini): What Is Sent (disclosure), Provider, Api Key (password field), Endpoint, Generation / Question Model, Generation / Question Effort, Max Output Tokens (32000), Refusal Fallbacks, Stream Replies; Confirm Changes, Save On Apply, Max Tool Calls Per Request, Allow Preview Capture (off), Collapse Tool Results After (3), Model Prices; Theme, Output Folder (`/Game/NameTBD_AI`), Library Folder; Start MCP Server (off), MCP Port, MCP Allow Writes, MCP token, MCP Save After Writes.

### Decisions made without asking
- **Preview = the real thing, live**: a request builds in the editor as it goes (so the model gets real results - compile errors, created paths) and ends on Apply / Discard of the whole request as one undo step, rather than staging writes before running them (staging can't return compile results). Starting a new request keeps an open card.
- One request = one transaction kept open across frames (as interactive drags do); edits the user makes during a running request join its step.
- Shipped content is **data** (JSON graphs and recipes), built into assets on first use, instead of binary .uassets in the patch; the plugin content path `/NameTBD/AI/...` is checked first so a release can ship them built.
- Niagara templates fall back to engine emitter templates + module constants (approximate) because authoring module stacks from code is version-fragile (as the plan said); the recipes document the intended stacks.
- Docs come from live reflection at run time, not a build-step generator: always in step with the code, nothing to regenerate.
- Tool names: `get_context` (was describe_selected), `add_widgets` (a nested tree, was add_widget), `set_widget` (was set_widget_property), `add_tracks` / `set_track` (keys are track fields: set_keys folded in), `build_ui_material` (was create_ui_material; also rebuilds), ready-made buttons via add_widgets "button" (no create_ready_made_button), Shape / Design Targets, Looks, Flow List settings via set_widget's paths (no dedicated tools); `animate_widget` added for "make it bounce in".
- Anthropic defaults: Opus 5.5 to build, Haiku 5.5 for questions (the plan asked for a cheap and a strong model); refusal fallbacks on by default.
- The MCP token persists in the per-user settings (not per editor session), so a client set up once keeps working; Regenerate Token revokes.
- Effort / thinking: no `thinking` field sent; OpenAI-side reasoning effort not sent (models differ).

## Widgets that read well and look finished (widget building)
> **Standing expectation (the user's own words):** "There could be more use cases that users desire that I haven't thought of, but would be expected in a production-grade application."

- **Asked:** "AI widget creation needs to be vastly improved." Given "Create a Widget Blueprint WBP_VideoControls with parent class MediaBoxTransportBar... a Button named PlayPauseButton (play icon)... a Button SubtitlesButton labelled CC. Use the dark theme", the model laid it out well but "filled every button with gibberish, malformed text in a light color with made it illegible on the default button (it always does this light text on light background pattern for text)" and didn't style the buttons (only a dark grey background).
- **Why (found by reading; the chat log of that run wasn't available):** an engine Button keeps the engine's light grey style (the theme only reached the plugin's roles and ready-made buttons); a Button has no Text field, so `text` on it was dropped and the model added Text Blocks in the dark theme's light text colour on that light grey; "play icon" and friends were written as symbol characters (▶ ⏸ 🔊) the default font doesn't draw - boxes and garbage.
- **As built** (`NameTBDAIWidgetStyling.h/.cpp`, `NameTBDAITools_Widgets.cpp`, `Resources/AI/Icons.json`, `Roles.json`):
  - **Engine widgets themed** (`ThemeEngineWidget`) as they are built, before the spec's own settings: Button (rounded, palette fills per state, outline, padding, readable foreground; `variant` primary = accent filled, secondary = raised and outlined (default), ghost = no fill until hovered), Slider (track, thumb, accent progress where the engine has it), Progress Bar, Check Box, Editable Text Box. Style structs are read and written by property name, whatever accessors the engine version has. `theme: false` keeps the engine look. apply_theme re-themes them in the other palette (remembered as `$engine:<variant>` beside the roles).
  - **Button content:** a Button (engine, or a plain Context Menu Button) given `text` / `label` and / or `icon` and no children gets them built inside it - a Text Block (strong body type) and / or an SVG Image, side by side in a Horizontal Box - in the colour that reads on its fill.
  - **Icons:** `icon` takes a name from `Icons.json` (46 icons, 24x24 outline: play, pause, stop, next, previous, forward, rewind, volume, volume_low, mute, subtitles, fullscreen, exit_fullscreen, settings, close, check, plus, minus, chevrons, arrows, menu, search, home, heart, star, info, warning, refresh, lock, user, trash, edit, download, upload, more, loop, mic, bell, speed, picture_in_picture; plus aliases: cc, captions, volume_up, volume_off, gear, x...) or an SVG / texture path. A named icon becomes an SVG asset once (`<Output Folder>/Icons/SVG_Icon_<name>`, Draw In White so the widget's colour tints it) and an SVG Image (`WidgetSVGImage`, `icon_size`); a texture path goes into an Image's brush. `list_options icons`.
  - **Symbols the font can't draw:** a text made only of a known symbol ("▶", "⏸", "🔊", "✓"... `Icons.json` glyphs) becomes that icon (and a text / image class asked for it becomes an SVG Image); other such characters (media and technical symbols, geometric shapes, dingbats, enclosed alphanumerics, private use, emoji) are left out. Both are reported in the warnings so the model learns.
  - **Contrast check** (`FixContrast`) after every add_widgets, set_widget and apply_theme: each Text Block (with a set colour) and SVG Image is checked against what is behind it - walking up, a Button's fill (an engine texture style read as light grey), a Border's colour, a filled shape (gradients averaged), an earlier filling sibling in an overlay, translucent ones blended over what is behind them, else the theme's background - and below WCAG 4.5:1 (3:1 for text of 18+ and icons) takes the dark or light palette's text colour, whichever reads; each fix is a warning ("contrast fixed - ..."). Text in ready-made buttons is left to their style.
  - **Bound parts:** create_widget_blueprint returns `bound_parts` (the parent class's BindWidget / BindWidgetOptional names and classes, e.g. a Media Box Transport Bar's PlayPauseButton: Button); building a part with that name of a class that can't bind, or finding the name taken, is a warning.
  - **Roles:** button, button_primary, button_ghost, icon_button (engine Buttons by variant), toolbar (a dark translucent rounded bar to put a row in). Map.md: readability rules, buttons with text / icon, never symbols, bound parts, and the video controls example.
- **Beyond the request:** the theming covers every engine widget that ships light (sliders, check boxes, progress bars, text boxes) and re-themes on apply_theme; icons are a reusable library (one asset per icon, shared), aliases and the model's habitual glyphs map to them; contrast is enforced for any text the model writes, not only buttons, including translucent and overlay backgrounds; parent-class part binding is surfaced so controls actually work.
- **Decisions made without asking:** engine Buttons stay engine Buttons (a parent class binding `UButton` parts takes them; ready-made buttons remain the richer choice and are Buttons too). Theming happens before the spec's props, so the model can still override any field. Contrast fixes change the colour (and say so) rather than refusing the build. An unknown backdrop counts as the theme's background. Icons are generated SVGs (data in `Icons.json`, like the other shipped data), not binary content.
- **Still open:** Combo Box (String) theming (its menu rows), Spin Box, Multi-Line Editable Text Box; checking text over images and materials (unknown colours are skipped); icon-state swapping for a transport bar's Play / Pause (the bar's On ... Changed events) built by the AI; a capture_preview based contrast check of what is actually drawn.

## The plan it was built from

### What the user wants (added after DataBinding v1 / Shapes v1 - to be built in its own chat)
**Full AI integration that creates polished widgets from a prompt, start to finish in the UE editor, for rapid iteration.** Not a Q&A helper first: the headline is "describe a widget, get a finished, good-looking Widget Blueprint you can keep tweaking by prompt or by hand".

- **Acceptance test (use it verbatim):** *"Create a greeting card that says "Hello User" at the top left with a soft aurora glow at the bottom and faint circle particle effects that bubble from the bottom and fade upward."* Expected result, in one undoable step behind an Apply / Discard preview:
  1. `WBP_GreetingCard` (new Widget Blueprint, unique name), Overlay root, fixed size (~600x360), a Rectangle shape as the card (rounded ~24, dark fill).
  2. Text "Hello User", slot top left, padding ~32, large white font, on top.
  3. Aurora: a Rectangle along the bottom with a linear gradient fill (teal / green / violet fading to transparent upward) - or a shipped UI aurora material on the shape's fill - hit-test invisible; optional looping Widget Animation shifting its colors slowly (ping-pong).
  4. Bubbles: a Niagara UI system made from a shipped "Rising Bubbles" UI template (CPU, local space, sprite, upward velocity + drift, fade by age, soft-dot material), User Parameters set (rate, size, opacity ~0.25, rise speed, color); a Niagara Particles widget at the bottom center, hit-test invisible, between the aurora and the text.
  5. Compiled, saved, and summarized back (widget tree + key settings; optionally a preview capture for a multimodal check).
- **Rapid iteration is the point:** follow-ups ("make the glow purpler", "more bubbles", "move the text to the center", "add a pill button that says Continue", "make it bounce in") are each one or a few tool calls on the widget just made - the AI keeps the target in context (`describe_selected` / the last-built asset) and edits rather than rebuilds. Every edit is one undoable transaction.
- **"Polished" by default:** the tools apply house defaults so a first result already looks finished - spacing scale, corner rounding, font sizes, color palettes (light / dark), Motion presets (the ready-made buttons' Smooth / Snappy / Bouncy, the spring presets), entrance animations from track presets. The model chooses intent ("card", "title", "accent", "soft glow"); the tools turn intent into consistent values. A style/theme asset (palette + type scale + spacing + motion) the user can edit, read by every tool.
- **Can create, in scope:** Widget Blueprints and their widget trees (any UMG widget + the plugin's shapes - which can now hold children, Shape Box, Flow List, ready-made buttons, animated text, Niagara Particles), slot layout, properties; Widget Animation assets / timelines (tracks, keys, easing, springs, parameters); state machines; Widget Data Binder setups (triggers, List Bindings, Sample Sets - so "a leaderboard" works with sample data in the designer's Data Preview); Context Menu Button targets and Looks; presets.
- **Niagara for UI:** from **shipped UI-ready templates** (bubbles, sparkles, confetti, embers, glow ring, trail, rising sparkle loop), duplicated into a new `NS_` asset and tuned through User Parameters and a few safe emitter settings (CPU, local space, loop once, UI material / Material Remap). Validate with the Niagara Particles widget's compile checks. No free-form module-stack authoring in v1 (editor-internal, version-fragile); narrow module tools later only if real prompts need them.
- **UI materials - created too (in scope):** **The AI creates the entire material itself - asset, every node and connection, domain / blend settings, compile, fixing its own compile errors, save, and assigning it to the widget; the user never has to open the Material Editor (only C++ is suggest-only).** Unreal's editor API for material graphs is supported and stable (`UMaterialEditingLibrary`, MaterialEditor module - what Python editor scripting uses: create a `UMaterial`, add expression nodes, connect them to outputs, lay out, recompile), and a UI material is small: Material Domain **User Interface**, Blend Mode **Translucent** or **Additive**, Final Color + Opacity, usually times Vertex Color (which the plugin's shapes and Niagara UI feed). Three tiers, safest first:
  1. **Instance a shipped master** (most prompts): parameterized master UI materials shipped with the plugin - aurora, soft glow, shimmer sweep, gradient, noise fog, rounded vignette, ring pulse, dissolve. The AI makes a Material Instance and sets colors / speeds / intensities. Instant, can't break, looks good. The fast path for iteration.
  2. **Compose from blocks** (new effects - "scanline overlay", "heat shimmer", "aurora with drifting star specks"): a tool takes a small JSON graph (nodes, parameters, connections) and builds a new UI material through the editing library. Every tunable value is exposed as a parameter, so follow-ups ("slower", "more purple") become instance edits, not graph edits. The material's compile errors are returned so the model can fix the graph.
  3. **Material Functions** shipped for reusable pieces (soft circle, rounded-rect SDF, panning noise, color ramp), so tier-2 graphs stay short.
  - Used wherever the UI takes a material: a shape's fill or stroke (Along Outline for an edge glow), an Image brush, a Niagara UI renderer (or Material Remap), a button's Design Target - and animated / bound through the Widget Animation Material Scalar / Vector tracks and Animation Parameters.
  - Limits: the AI can't judge the look without the opt-in preview capture; Custom (HLSL) nodes allowed but sparingly; a new material compiles its shaders (seconds the first time), which is why tier 1 is the iteration path.
  - Greeting card: the aurora is an instance of the shipped aurora master; something unusual is built as a new material with its parameters exposed.
- **Out of scope / suggest only:** Blueprint graph logic beyond narrow tools (bind an event, add a Custom Event); C++ (copy-paste suggestions only); textures (no image generation).
- **Shipped content is part of the feature:** the Niagara UI templates, the master UI materials and Material Functions, and the default theme must ship with the plugin, or the AI has nothing good to pick from.
- **Seeing the result:** an opt-in tool that renders the designer preview to an image for a multimodal model to critique layout/contrast ("text overlaps the glow") and fix it - off by default for cost.

**Suggested v1 tool list (wrapping existing code, chiefly `WidgetAnimScripting` which already adds widgets, tracks, keys and parameters):** `create_widget_blueprint`, `add_widget` (with slot settings), `set_widget_property`, `set_shape_paint` (fill / gradient / stroke), `create_widget_animation` / `add_track` / `set_keys` / `apply_track_preset`, `create_niagara_ui_system(template, params)` / `set_niagara_parameters`, `create_material_instance(master, params)` / `set_material_parameters` / `create_ui_material(graph)` (tier 2, returns compile errors), `add_trigger` / `add_list_binding` / `add_sample_set`, `apply_theme`, `describe_selected`, `list_options`, `capture_preview` (opt-in). Expose through the **MCP server first** (drive and test from Claude Code / Claude Desktop immediately), then the in-editor chat panel. Deliver as `NameTBD_AIAssistant_v1.patch`; the greeting card prompt above is its acceptance test.

### Goals (the user's requirements)
- **Free for the plugin creator:** no hosted servers, relays, proxies or shipped API keys - nothing that bills the creator per use. Every token is paid by the plugin's user, through their own provider account (or free, with a local model).
- **As token-efficient as possible for the user:** no "research period" at the start of a chat. The model gets a small cached map, fetches details only on demand, and reads compact facts from tools - never whole assets or source.
- **Full expected functionality:** answer questions about the plugin, generate and edit Widget Animations, shapes, Context Menu Buttons (ready-made included), Flow Lists and presets, and diagnose problems on the selected widget - in the editor and from external assistants.
- Both surfaces: an **in-editor chat panel** and an **MCP server**, sharing one tool layer.

### Architecture
- **New editor-only module `NameTBDAI`** (never in packaged games; Fab: disclosed, opt-in, editor-only). Everything below lives there, except the generated docs (plugin `Resources/AI/`).
- **1. Tool layer (core, shared by both surfaces).** Each tool is a C++ function with a JSON schema; input is validated against the plugin's own structs, then written through the existing functions (`WidgetShapeAnimation`, Shape/Design Target APIs, Flow List presets, Widget Animation assets...). Not code generation - data.
  - Read tools (cheap, compact output):
    - `describe_selected()` - the selected widget(s): class, and only **non-default** settings as terse JSON (filtered, no full struct dumps).
    - `list_options(kind)` - valid enum values, presets, shape kinds, track types, spring presets, so the model never needs docs to know what's allowed.
    - `search_docs(query)` / `get_docs(topic)` - see Docs.
    - `get_asset(path, fields?)` - a Widget Animation / preset asset, optionally only some fields.
  - Write tools: `create_widget_animation`, `add_track` / `set_keys`, `set_shape_look` (a Shape Target state's Look), `add_shape_target` / `add_design_target`, `set_background_shape`, `apply_flow_list_preset` / `set_flow_list_settings`, `create_ready_made_button(kind)`, `save_preset`. Grow the list from real usage; each mostly wraps existing functions.
  - **Safety:** every write is one `FScopedTransaction` (Ctrl+Z reverts it), touches only the selected or named assets/widgets, and the chat shows a preview ("adds 3 tracks to WA_Hover") with Apply / Discard before writing. Validation errors return short, actionable messages the model can correct from.
  - Tool definitions (names, descriptions, field descriptions) are generated from the same reflection data as the docs, so the schemas themselves teach the model most of what it needs.
- **2. Docs, generated, shipped, searched locally (free).**
  - A build/editor step extracts tooltip strings (`NameTBDTooltips.h`), UPROPERTY / UCLASS / UENUM comments and enum tooltips into **small topic files** (a few hundred tokens each, e.g. "Flow List: Play On Selection", "Shape Target Looks", "Hold Button"), plus a hand-written **map** (see below). Regenerated on every release, so docs never drift from code.
  - Local search: a keyword (BM25-style) index built with the docs; optional small precomputed embeddings. No service, works offline.
- **3. In-editor chat panel** (dockable tab, `Window > NameTBD AI`).
  - **Bring your own key:** provider (Anthropic, OpenAI, Gemini) or any **OpenAI-compatible endpoint** (covers Ollama, LM Studio, most local servers and gateways) + model + key. Stored per user (Editor Per-Project/User settings, `config = EditorPerProjectUserSettings`), never in `Default*.ini`, never committed; the plugin ships no key.
  - Thin adapter per provider over `HttpModule` + `Json`: streaming replies, tool calls, prompt caching flags. Unreal's HTTP is enough; no SDKs.
  - Two model choices: a cheap default for Q&A and a stronger one for generation (user picks both).
  - UI: chat, "context" chips (selected widget/asset auto-attached as `describe_selected` output only on request), preview/apply cards for writes, per-request token/cost estimate, clear errors (invalid key, rate limited, model has no tool support).
- **4. MCP server** (same tools, same docs).
  - Runs locally, started by the plugin from the editor (stdio launcher or localhost HTTP/SSE bound to 127.0.0.1 only, with a per-session token). Talks to the running editor, so tools act on the open project.
  - Exposes: **tools** (the tool layer), **resources** (doc topics), **prompts** (the map, plus a few task prompts: "make a hover animation", "debug this Flow List").
  - The AI is whatever the user already runs (Claude Desktop, Claude Code, Cursor...) - their subscription/key. A "Copy MCP config" button in settings writes the client JSON for them.

### Token efficiency (the core design)
- **Map, cached:** a fixed system prompt of ~1-2k tokens: what each system is (Widget Animations, Flow List, Shapes, Context Menu Button, ready-made buttons), key terms, and which tool answers what. **Byte-for-byte stable** across chats and versions-of-a-session (anything per-chat goes after it) so provider prompt caching applies: Anthropic (explicit `cache_control` breakpoint after the map and tool list), OpenAI (automatic prefix caching), Gemini (context caching). Cached tokens cost ~10% after the first request. Tool definitions are also stable and sit inside the cached prefix.
- **Details on demand:** no docs in the prompt beyond the map; the model calls `search_docs` / `get_docs` for the one or two topics a question needs (a few hundred tokens).
- **Facts from tools, not reading:** `describe_selected` returns only non-default values; `list_options` returns enums/presets; outputs are compact JSON, no prose, no full structs, no source files.
- **Short conversations:** new chat per task is cheap (cached map); long histories are trimmed or summarised by the panel; tool results older than a few turns are collapsed to one-line summaries.
- **Lean writes:** write tools accept partial data (only the fields to change); defaults fill the rest.
- Target: ~1-2k cached tokens of fixed prefix + a few hundred tokens per question → cents or less per chat, no warm-up.

### Cost to the creator: zero per use
- No relay, proxy, hosted search or analytics; docs are searched locally; MCP runs on the user's machine.
- Remaining creator costs: one-off API usage while developing/testing; support (mitigated by clear in-editor errors and setup docs).
- No commercial agreement with providers needed: users call public APIs with their own credentials under their own provider terms.

### Disclosure (Fab listing + settings page)
- AI features are optional, editor-only, and need the user's own provider account (or a local model); usage is billed by that provider; the rest of the plugin works without them.
- Exactly what is sent: the map, tool definitions, the user's messages, and tool outputs (selected widget settings, requested doc topics) - never the whole project. Show provider/model and a per-request token estimate.

### Build order
1. Tool layer + generated docs + local search (useful alone, testable without any model).
2. MCP server on top (small; lets the tools be exercised from existing assistants immediately).
3. In-editor chat panel + provider adapters (Anthropic, OpenAI, Gemini, OpenAI-compatible) + caching + previews.
4. Grow tools from real requests; keep the map stable.

### Risks / notes
- Local/small models handle tool calls worse: strict validation, short error messages, and a "model lacks tool support" check.
- Provider APIs change: keep adapters thin; the OpenAI-compatible adapter is the fallback.
- Blueprint graph generation is fragile; keep to narrow, well-tested tools (e.g. bind an event) rather than free-form graphs. C++ generation stays copy-paste only.
- Never write outside the selected/named targets; every write undoable.

# Reliable material generation (AIAssistant v2 - done: `NameTBD_AIAssistant_v2.patch` + `_v2_fix1` ... `_v2_fix5`) - goal: any model builds a working material first try ~95% of the time

## Why it failed (v1)
- Reported after testing over MCP with Claude Desktop: Claude needed several tries to build materials without errors, until it was given computer access.
- The model wrote a node graph from memory (class names, pin names / indices, float widths, UI-domain rules) and learnt of each mistake only after a full build + shader compile, one error at a time.
- Found while building v2: three shipped graphs (`ColorRamp`, `Dissolve`, `Shimmer`) used node type `Lerp`, which is no expression class (`LinearInterpolate`) - so `MF_UI_ColorRamp`, and through it `M_UI_Aurora` and `M_UI_Gradient`, built broken. Fixed in the data, and the library rebuild-on-change (above) repairs projects that built them.

## As built
- **The order models are told to work in** (Map.md, tool descriptions, `Docs/materials.md`, MCP prompt `make_material`): (1) a master instance; (2) a master plus nodes - `build_ui_material {from_master, graph}`, "master.FinalColor" / "master.Opacity" in the graph = the master's outputs (`MergeWithMaster`; an id clashing with the master's is refused); (3) a new graph from macro nodes, a few maths nodes and `{"param": Name, "value": v}` for every tunable. `from_master` with no graph makes an instance.
- **Node catalog** `Resources/AI/MaterialNodes.json` (~50 nodes): name, aliases (`Lerp`, `Mul`, `TexCoord`...), pins (aliases, optional, width rule `1|2|3|1|out|any`), output width rule (`max:A,B`, `same:Input`, `sum:A,B`, `mask`, fixed, `list` = from the engine's output masks), prop aliases (`name` -> ParameterName, `value` -> DefaultValue...), category; plus `ui_errors` / `ui_warnings` (SceneTexture... / WorldPosition...) and compile-error `hints`. Matched against the engine at run time: the class by `FindFirstObject<UClass>("MaterialExpression"+Name)`, pins by the class default object's `GetInput(i)` / `GetInputName(i)`, outputs and their widths by `GetOutputs()` masks (a mismatch with the catalog is logged, the engine wins). Nodes outside the catalog still work, checked by their reflected pins only.
- **Macro nodes** `Resources/AI/MaterialMacros.json` (13): glow, soft_circle, ring, rounded_rect, linear_gradient, radial_gradient, color_ramp, panning_noise, time_wave, uv_tile, band (sweep / shimmer), stripes (scanlines), remap. One node in a graph, expanded to its tested subgraph (ids `<macro>/<inner>`, nested up to 4 deep); every input optional with a default; outputs by name (`g.Mask`) or the first by the bare id.
- **`NameTBDAIMaterialGraph::Prepare`** (`Source/NameTBDAI/Private/NameTBDAIMaterialGraph.*`): reads any form models write (nodes as a list or a map by id, settings on the node itself, inputs as an object or a positional list, wires as `connections` / `edges` [{from, to}] or [[from, to]], refs as strings or {node, output}), expands macros, turns constants / `{"param"}` / `$uv` / `$time` into nodes (a hex color is a float3 unless it has a real alpha; a [x, y] param is a VectorParameter's RG; the same param name reuses one node, a number/color clash is an error), then checks everything and returns **all** problems at once, each `"<node id>: <what to do>"`: unknown node (did-you-mean over catalog + aliases + macros), unknown pin (lists the real ones), unknown output, missing node ref (did-you-mean), required input unwired, duplicate ids, loops, widths on every wire (scalars broadcast; other widths must agree), AppendVector over float4, ComponentMask with no / out-of-range channels, unknown props (lists the real ones), parameter name clashes, Custom code / input names, a missing / unknown library function, UI-domain nodes, outputs a UI material doesn't have.
- **Repairs** (listed under `fixed`, counted in the stats): type / pin aliases (incl. X/Y/In1/In2 for A/B), float4 meeting float3 (masked to RGB), float2 into a float3 pin (append 0), float3/4 into a float2 pin (mask), a channel picked from a one-output node (`m.y` -> ComponentMask), a color into Opacity (alpha of a float4, else R), float4 into FinalColor (RGB), BaseColor in UI -> FinalColor, Opacity <-> OpacityMask by blend, Opaque with Opacity -> Translucent, a Noise with no Position (UV x 8, appended 0), a library function's unwired UV (the widget UV), Custom code without `return`, the same parameter made twice, unused nodes dropped, a parameter with no name (named from its id). **Added** to every UI material (listed under `added`, not counted as slips): Saturate on Opacity when its source isn't provably 0..1, and the VertexColor tint (FinalColor x RGB, Opacity x A, Opacity = A when missing) unless the graph uses VertexColor or says `"tint": false`.
- **`validate_material`** (read-only tool): the same check, nothing built. `build_ui_material` refuses (isError, no asset made) while the graph has errors; a compile failure is isError too, with `compile_errors` each tied to its node (by the "(Node X)" in the text matched to `GetErrorExpressions()`, else by position, else the only Custom node) plus a hint from the catalog.
- **Custom HLSL** (escape hatch): `{type: "Custom", code, output: float1..4, inputs {name: ref}}` - the inputs become `FCustomInput`s in order; names checked as HLSL identifiers.
- **Stats**: every validate / build per model (`FNameTBDAIToolContext::Model` - the chat's "Provider:model", the MCP client's `clientInfo` name + version) in `Saved/NameTBDAI/stats.json`: calls, materials, first_try (no failed validate / build before the build that compiled), first_try_rate, instances, fixed, compile_errors, and problem counts by kind.
- **Eval** `Resources/AI/Evals/`: `material_prompts.json` (40 prompts, each with the sensible path: 10 instance, 4 extend, 25 graph, 1 any) and `run_material_eval.py` (stdlib only): runs them through Anthropic / OpenAI / OpenAI-compatible / Gemini with the editor's own map and the material tools over MCP (clientInfo `eval:<provider>:<model>`, so stats.json splits by model), assets into `<Output Folder>/Eval/<model>`; reports path taken, first try, worked, calls, tokens; `--validate-only` checks graphs without building (no assets, no shader compiles); results in `Saved/NameTBDAI/evals/`.
- **list_options**: `material_nodes` = the catalog one line per node + the macros + the rules (~1.8k tokens, on demand), `material_nodes <Name>` = engine pins (optional, widths), outputs and widths, props; `material_masters <Name>` = the master's params and graph.

## Decisions made without asking
- Patch named `NameTBD_AIAssistant_v2.patch` (the AI Assistant's next step, not a fix).
- Graphs with errors are not built at all (no half-made asset); repairs are applied silently but always listed, so a model learns them.
- Width rules follow the HLSL translator's (scalars broadcast, Lerp alpha scalar or equal width); where a repair could change meaning (a Lerp alpha wider than its values, a float2 into a color) it is an error with the fix spelled out, not a guess.
- The VertexColor tint and Saturate on Opacity are added to every UI material (opt out with `"tint": false`), so widget tint / opacity and particle colors always work - the masters already did this.
- Macros expand inline (no Material Function assets needed); the library functions still work through MaterialFunctionCall.
- The eval talks to the editor over MCP rather than a commandlet: it measures the real tool loop per model, and the editor keeps per-model stats anyway.
