# Buttons (Context Menu Button, ready-made buttons)

## Context Menu Button: any shape (Buttons v1)
- **Shape Style** (was Background Shape): the button's background drawn as a vector shape instead of the Style brushes. Authored on a **Self Shape Target** (see "Shape Style, presets, instance overrides" below); stored on the button as `BackgroundShape` (`TSubclassOf<UShapeWidget>`) + `BackgroundLook` (property bag laid out for it), both hidden from the Details. `SyncBackgroundShape` lays the bag out and, only once a Slate button exists (never on the WBP template), makes `BackgroundShapeWidget` (transient package, `RF_Transient`), writes the Look onto it and hands it to `SContextMenuSlateButton::SetBackgroundShape`, which swaps the brush layer's content (`SShapeBox`) from `SContextMenuButtonBrush` to an `SWidgetShape` - so the shape's Transform, hit area and core transform work exactly as for the brush. Tinted by Background Color (a Design Target's Tint on Self).
- **Looks on Shape Targets** (shown as **Style Settings**): `FContextMenuShapeStateSettings` gained `Look` (bag, FixedLayout) and the mirrors `bHasLook` (this state has a Look) and `bIsVectorShape` (hide the Shape Box `Shape`). **Sparse (fix3):** only states the target overrides carry a Look; the Base Shape of a non-Self vector shape never does - its base is the shape as authored in its own Details - and a state without a Look falls back to the base (`BaselineLook` at runtime, `WriteLook`'s Fallback in previews). On a **Self** target with a Shape Style the Base Shape's Style Settings are the style as authored (a mirror of `BackgroundLook`). `RefreshShapeTargetLooks` lays out the overridden states' Looks (from the target widget, or Background Look for Self), mirrors the Shape Style into every Self target (`MirrorShapeStyleToSelfTargets`) and empties every other Look - run on every edit, on palette creation and when the Details open.
  - Only settings whose Look differs from the shape *as authored* in some state are written (`GatherLookProperties` vs `FindLookBaseline`: Background Look for Self, otherwise captured the first time a Look reaches that shape, kept in `LookBaselines`). They blend at the Shape channel's speed/curve/delay (`WidgetShapeAnimation::WriteBlend`, start captured into `StartLook` on each state change). Designer previews write them at once (`WriteLook`).
  - Vector targets: Transform goes on the shape itself (never on a Shape Box around it); a Self vector background gets no Shape Box shape.
- **Design Targets on shapes** (`GetDesignShape`: a shape widget, or a button's Shape Style **while it is filled**): Tint = Fill color, Outline Tint = Stroke color (`GetOutlineShape`: the Shape Style filled or not), Brush Texture / Material / material parameters = `GetImagePaint()`'s image. With the Shape Style's fill off they act on the button's own brush, which shows inside the outline.
- **Design Targets show SVGs:** a state's brush channel has **Brush Image Source** (`EWidgetImageSource`, default Texture 2D; it now carries the channel's inline toggle) with **Brush Texture** or **Brush SVG** under it (placement overrides: the same three under Override Brush Texture). Swapped at the state change like a texture (a Switch button: a play SVG for Normal, a pause SVG for Enabled).
  - On a shape (or the button's Background Shape), the Image paint is set to Image Source SVG. On an **SVG Image**, its SVG is set (`ShowSVGOnWidget`).
  - On an **Image, Border or Button** (the Context Menu Button itself without a Background Shape too), the brush becomes the SVG drawn at the widget's size on screen (`FContextMenuTargetSVG` in `TargetSVGs`: an `FWidgetSVGBrush` with the brush or style it had before). Each state brush keeps its look (Draw As, Margin, Tint, outline, Image Size). `TickTargetSVGs`, an active timer on the button running while any is shown and restarted in `OnWidgetRebuilt`, pushes a new drawing in when the widget's size changes. `StopSVGOnWidget` puts the old brush or style back before a texture or the baseline goes on.
  - Baselines: `ExtractWidgetSVG` (a shape's SVG paint, an SVG Image's SVG) is restored like the texture baseline, at runtime and by `ClearDesignPreviews`. A shape's texture baseline ignores a leftover brush under an SVG paint (`DrawsBrush`).
- **Self** (`SelfTargetName`): target dropdowns offer Self for the button; a stored button name still works. `FindWidgetInButtonTree` also matches a name without its instance number among the button's own widgets (Label vs Label_1), so pasted/duplicated buttons keep their targets.
- **Target ID / Active (runtime targets):** every Shape and Design Target has an optional **Target ID** (`TargetId`) and **Active** (`bActive`, default on). Inactive targets are skipped by the runtime blend (`ApplyTransitions`) and the designer preview (`ApplyDesignPreviews`); their runtime entries are kept, so switching one on blends from where its widget is. Blueprint (`Context Menu Button|Targets`): **Set Target Active** (every target with the ID), **Set Target Variant** (on for the ID, off for every other target *with an ID* on the same widgets - a volume icon's Full / Half / Muted Design Targets on one Image, a record button's Idle / Recording Shape Targets on one shape), Is Target Active, Get Target IDs, **Get / Set Shape Target By ID**, **Get / Set Design Target By ID** (the whole struct; the ID kept), **Set Design Target Image** (an SVG or texture into the Base Design and every overridden state - an icon that follows a value), **Set Shape Target Transform** (one state's Transform, else Base). All go through `ApplyChangedTargets`: the changed entries re-resolve their goal and restart their blend from where they are; one switched on takes the transform of the target switched off on the same widget (else the widget's Render Transform) and reads its design channels off the widget; brush / material swaps happen again; `bInstant` snaps (`ApplyTransitions(0, true)`), else the visual timer runs. In the designer they repaint the preview.
- **Exit speed:** Shape Targets and Design Targets have **Exit Interpolation Speed** (inline toggle `bSeparateExitSpeed`, off = the old behaviour): the speed used while blending back to Normal (unhovered, switched off), for both shape channels.
- **Layout size hook:** `WantsLayoutSizeChanges()` / `HandleLayoutSizeChanged(NewSize)` (protected virtuals, off by default): `SContextMenuSlateButton::OnPaint` reports a new layout size, deferred to the next core tick (as the enabled-state change is).
- New settings: **Click Only Enables** (a click never un-enables; off on the ready-made Radio/Tile since fix6), **Repeat While Held** (Hold), **Progress Widget / Progress Value / Progress Range** (Hold: a shape value or a Progress Bar follows the press duration, via `BroadcastPressProgress`).
- **Palette drops (fix4):** `OnCreationFromPalette` builds nothing - it only sets `bPendingDefaultContent` (editor-only data). The editor module (`StyledButtonsEditor`) builds the parts once the button has really been placed (fix5): after any compile of the Widget Blueprint (a drop always compiles) and whenever a Context Menu Button's Details are shown, it schedules `BuildPendingInBlueprint`, which runs on a later tick once no drag-drop is in progress and the blueprint isn't compiling, and builds every pending button **of the Widget Blueprint's own tree hierarchy** - never the designer preview copies (which is what the UMG Details panel shows; their blueprint is found through `WidgetGeneratedByClass`). The pending flag is consumed before the transaction (`ConsumePendingDefaultContent`), so undoing the build leaves the button empty instead of rebuilding it; the build (`BuildDefaultContentForEditor`) is one undoable transaction, every part gets a GUID, the blueprint is marked structurally modified. Before every Widget Blueprint compile (`GEditor->OnBlueprintPreCompile`), every widget in its tree without a GUID gets one (through reflection on `WidgetVariableNameToGuidMap`); next tick, parts left behind by discarded drop previews (outside the hierarchy, their ready-made button already moved out of the tree by the designer) are moved to the transient package. **Rule:** never create widgets in a Widget Blueprint's tree from `OnCreationFromPalette` - the designer calls it for every drop preview and gives no GUID to children.
- Hooks for subclasses: `HandleNavigation(EUINavigation)` (Slate `OnNavigation` asks first; true keeps focus), `BuildDefaultContent()` (called from `OnCreationFromPalette`, and from `RebuildWidget` at runtime when `ShouldBuildDefaultContentWhenEmpty` and the button is empty), `GetLastPressPosition` (fraction) / `GetLastPressScreenPosition` (unset for key presses; `SContextMenuSlateButton` records presses in `OnMouseButtonDown`/`OnTouchStarted`, clears on `OnKeyDown`).
- `FContextMenuButtonDetails` refreshes Looks before laying out and, after a target widget / Shape Style / preset / override toggle / Shape Targets array change, makes only that list's rows again next tick (`IPropertyHandle::RequestRebuildChildren` on the Shape / Design Targets handle) - the rest of the panel stays put; a Button Preset picked lays the whole panel out again (`ForceRefreshDetails`). **Rule:** its rows go onto the properties' own rows (`EditDefaultProperty` + `CustomWidget`), never into `EditCategory("Context Menu Button|X")`: in this panel that path is a sub-category of Context Menu Button, and editing it by name makes a second top-level category that lists the property again.

## Context Menu Button: Shape Style, presets, instance overrides
> **Standing expectation (the user's own words):** "There could be more use cases that users desire that I haven't thought of, but would be expected in a production-grade application."

- **Asked:** Base Design not working until Override Normal Design is ticked; "Separate Transform And Shape" renamed "Shape Has Separate Interpolation", its fields hidden (not greyed) when off; chamfer X doing nothing until Y > 0; target widget on Design / Shape Targets defaulting to Self; Shape Status and Animation Status removed; Background Shape moved into the Shape Targets with every state, renamed (Shape Style), its look renamed and without its checkbox; the button's design showing when the Shape Style's fill is off (default off); the override set-up made a tick instead of a hand-made variable and events; design / shape presets as presets (assets, the plugin's pattern) instead of Project Settings; a whole button saved as a preset; "Invalidates Button" -> "Cooldown Sets Disabled State"; the button group settings in their own category under Settings; the Preview category (mode dropdown) removed; the toolbar's Idle / On -> Normal / Enabled; the toolbar's double divider.
- **Base Design fix:** two causes. (1) `PostLoad`'s old-layout migration ("a state that differs from a fresh one was authored flat: switch its override on") ran on every load of every target, and (2) `SyncMaterialParametersEditor` wrote Base Design's material and a parameter list into every state, overridden or not (also a state ticked then unticked keeps its copy) - so on the next load those states came back overridden with stale values and no longer showed Base Design. Now the migration only runs on a target in the old layout (Base Design fresh and no override on), and the sync writes only Base Design and overridden states. Also: `ShowPreview` None (an older default, no longer selectable) showed the designer's widgets without their designs - `PostLoad` makes it Normal.
- **Targets:** `TargetWidgetName` defaults to `Self` on both target kinds. The Design / Shape **Source** + **Preset Name** fields (Project Settings) are hidden legacy (`DesignSource`, `ShapeSource`, `PresetName`); the states are always shown. **Shape Has Separate Interpolation** (`bSeparateTransformAndSize`, display name only) with `EditConditionHides` on Shape Interpolation Speed / Curve / Overshoot / Delay (targets and the legacy struct).
- **Shape Style on Self targets, per state:** shown on the **Base Shape and every state** of a Self target as `FContextMenuShapeStateSettings::ShapeStyleClass` ("Shape Style", mirror `bIsSelfTarget` per state). The Base Shape's is the button's Shape Style (`BackgroundShape`; mirrored into it by `MirrorShapeStyleToSelfTargets`, and `FContextMenuShapeTarget::ShapeStyle` is now a hidden mirror kept for presets / older data). A state's: None follows the Base Shape (a state switched on starts with None); a style of its own swaps the background to that kind of shape in that state - `RefreshShapeTargetLooks` lays the state's Look out for it (a new one from Background Look's shared settings; from no button style, Fill off); at runtime `SwitchBackgroundShapeForState` (on a state change of the Self runtime target) takes the widget for that kind (`GetBackgroundShapeWidgetFor`: the Shape Style widget, or one transient widget per other kind in `StateStyleShapeWidgets`), lays the blend's start out for the new kind from what was showing (shared settings blend, the shape itself switches), blends every setting of it towards the state's Look, and paints it (`ShowBackgroundShape`; `ShownBackgroundShape` is what Get Shape Style Widget, design channels and the hit shape read). The designer preview / toolbar show it the same way. Picking the Base Shape's (`AdoptShapeStyleFromTarget(.., bStyleEdited)`) -> `ChangeShapeStyle`: `BackgroundShape` set, `BackgroundLook` laid out again keeping shared values; **picked from none it starts with Fill off** (`bFill` false in the bag). Editing a Self target's Base Shape Style Settings is the style's settings edit (`BackgroundLook` takes them, then `PropagateBackgroundLookEdit` into the states that still had the old value); told apart from a Base that only still mirrors an older style by `BackgroundLookSnapshot` (bFromDetails). Every Self target mirrors the one style. **Designer copy:** the UMG Details edit the designer's preview copy and copy only the edited member (`ShapeTargets`, whole, with no array index) to the Widget Blueprint's own button - not `BackgroundShape` / `BackgroundLook`, so its next mirror put the old style back (the pick "didn't stick"). Now an edit of the list that changes the style or its settings on a preview copy writes them onto the template too (`WidgetEditorHooks::FindDesignerTemplate`, `Modify`), and a whole-list set with no index (that copy, a paste, a reset) adopts the first Self target whose Shape Style differs, then the first whose Base Style Settings differ. `EnsureSelfShapeTargetForStyle`: a style always has a Self target to be authored on (an identity one is added on load / refresh when none is left - deleting the last Self target therefore doesn't clear the style; Shape Style None does). Blueprint: **Set Shape Style**, **Is Shape Style Filled**, Get Shape Style Widget.
- **Unfilled Shape Style:** whenever the shown shape's live `bFill` is off, `SContextMenuSlateButton::OnPaint` hands the state's style brush to the painter (`SWidgetShape::SetUnfilledBrush`), which fills the shape with it - its image across the shape's box, or its tint without one - cut to the outline, under the stroke, with the Background Color and Design Target writes. (It used to be drawn as a plain box under the shape: with a new style's Fill and Stroke both off the button showed no change - "the style doesn't apply".) Design channels on Self (Brush Texture / SVG, Material) go to the brush when the style as authored is unfilled (`IsShapeStyleFilled`), to the shape's paint when filled; Tint is Background Color either way.
- **Presets (assets, the Pointer Effects / Widget Path pattern):** `UContextMenuDesignPresetAsset` (Base Design, overrides and states, speeds), `UContextMenuShapePresetAsset` (state shapes with their Style Settings, overrides, interpolation; **Sets Shape Style** + Shape Style when saved from a Self target), `UContextMenuButtonPresetAsset` (`ButtonClass` + `Settings`, a bag of every property `GetButtonPresetProperties` returns: the button's and its subclasses' Details settings down to UButton's Style / colors / click methods, plus `BackgroundShape` / `BackgroundLook`; not Button Preset, Instance Overridable, Button Tag, Button Text Widget, Show Preview, the animation preview, read-only or transient ones; `GetOptions` metadata dropped so the asset's Details don't call button functions). Each target has **Preset** (`PresetAsset`); the button has **Button Preset**. Picking copies the preset in (`ApplyTo`, `ApplyButtonPresetSettings`) and keeps the link; any edit of what the preset covers clears the link (targets: any field but Target Widget / Target ID / Active / Preset; button: any property in the preset list). **Linked = untouched**, so `PostLoad` (`RefreshLinkedPresets`) takes linked presets again: edits made to a preset asset reach every button following it the next time it loads. Details rows (`FContextMenuButtonDetails`): **Save As Preset... / Update Preset** under the Button Preset picker (its value cell); **Save As Preset** (a menu of the targets) on the Shape / Design Targets header, after the element count and + / bin - made from the Widget Blueprint's own button (never the designer copy, whose design channels hold preview writes) through `WidgetEditorHooks::CreateAsset`. Blueprint: Apply Button Preset, Copy To Button Preset, **Apply Shape / Design Preset By ID** (a whole look swapped at runtime, blended).
- **Project Settings presets retired:** `UInfoCardDeveloperSettings::ContextMenuShapePresets / ContextMenuDesignPresets` are `UPROPERTY(Config)` only (hidden), kept for `MigrateProjectSettingsPresets`: on load, a target still naming one gets it copied into its own states once (a design preset's five states become overrides, Normal also the base; a shape preset's Transforms / Shape Box shapes, Style Settings kept) and becomes Custom. A target made in the editor is made Custom on its first `PostEditChangeProperty`, so it is never mistaken for a legacy one (the legacy field's C++ default stays Use Project Settings on purpose: old targets saved at that default load as it).
- **Instance Overridable** (`bInstanceOverridable`, in Settings): ticked, `FContextMenuButtonDetails::SyncInstanceOverridable` (next tick, one transaction, one compile) adds to the Widget Blueprint the 4 dispatchers (`On{Button}Clicked(bShouldDestroyCard, bEnabling)`, `EnabledStateChanged(bIsEnabled)`, `Hovered(bHovered)`, `PressCompleted`) and the Instance Editable `{Button}InstanceOverrides` variable, stamped with Target Button Name. Unticked: the blueprint's own overrides variables claiming the button and its own `On{Button}...` dispatchers (declared in this blueprint, not inherited) are removed - variable, then signature graph, as My Blueprint deletes one - in one undoable step; nodes elsewhere bound to them show broken. **Descriptions:** the variable's (`MD_Tooltip` through `SetBlueprintVariableMetaData`) says it was generated by Instance Overridable on the button and must not be deleted or renamed; each dispatcher's (its entry node's `MetaData.ToolTip`) says what calls it, the same. **Rename:** `UContextMenuButton::PostRename` (renamed in place, same outer) broadcasts `OnRenamedInEditor`; `FContextMenuButtonDetails::Register` (module startup) follows it for the Widget Blueprint's own button (not preview copies, not while transacting) and next tick `RenameInstanceOverridable` renames the button's own dispatchers (`RenameMemberVariable`, and the signature graph if that didn't) and the variable when it has the generated name (one named by hand keeps its name), re-describes them, compiles, re-stamps Target Button Name; a name already taken is kept and reported. Placements keep their values (blueprint variables keep their GUID through a rename). An undone rename (no `PostRename`) is caught when the Details open (`ReconcileRenamed`: a ticked button with neither variable nor dispatchers, and exactly one overrides variable pointing at a widget that is gone). **Notifications:** every add / remove / rename shows the editor toast (bottom right) listing what changed; a failed rename shows as failed. Its tooltip (name and checkbox) says what placements get, then what ticking does (`GetInstanceOverridableTooltip`). A button whose blueprint already has a claiming variable shows ticked when its Details open. The old **Add Overrides Variable** / **Add Matching Dispatcher** buttons are gone. Finding the variable at runtime is unchanged (declaring one by hand still works).
- **Cooldown Sets Disabled State** (`bInvalidatesButton`, display name; Cooldown Duration and it hidden while Has Button Cooldown is off): `ResolveButtonState` returns Disabled while `bIsOnCooldown`; `UpdateButtonState` at the start and end. It used to set the Visibility to Self Hit Test Invisible and back to **Visible** (overwriting an authored visibility) with no visual change. Is Enabled and the enabled state are untouched. Blueprint: **Is On Cooldown**, **Get Cooldown Remaining**.
- **Details layout:** **Button Group** category (`Context Menu Button|Button Group`) right after Settings: Unenable All Other Group Buttons On Enabled, Button Group, Group Index. Removed from the Details: Shape Status (property and `RebuildShapeTargetStatus` deleted), Animation Status (`ButtonAnimationStatus` kept as a hidden transient string), the Designer Preview struct (`DesignerAnimPreview` hidden; its Mode reset to Off on load).
- **Toolbar:** Normal / Hover / Press / **Enabled** / Disabled; **In / Out** (shown when the button has Anim In / Anim Out: `PlayDesignerAnimPreview(bOut)` sets the copy's preview mode to Play In / Play Out Once, through Off to replay); the entry is now in the selected widget's animation section (`FWidgetAnimBuilderToolbar::SelectedWidgetSectionName`): a toolbar draws a divider at the start of every section, collapsed controls or not, so the two sections drew two dividers with an empty gap.
- **Beyond the request:** linked presets follow later edits of their asset; Update Preset; Save As Preset per target from a menu; Apply Shape / Design Preset By ID at runtime; Set Shape Style / Is Shape Style Filled from Blueprint; the toolbar's In / Out (the removed dropdown's job); Is On Cooldown / Get Cooldown Remaining; a cooldown no longer overwrites an authored Visibility; Instance Overridable marks itself for existing set-ups and removes its variable when unticked; descriptions on the generated dispatchers too (not only the variable); per-state Shape Styles blend the settings two kinds share across the swap, preview in the designer and toolbar, and go into Shape Presets with the states; a rename made by undo caught up when the Details open; a rename that would collide reported instead of forced; chamfer with one leg (Shape Box, every user of it).
- **Decisions made without asking:** the Shape Style lives on Self Shape Targets but is stored once on the button (one background, several Self targets for Target ID variants); only Self targets' Base Shape carries Style Settings (another vector shape's base stays its own Details, where it is authored); presets copy-on-pick with a link (the plugin's pattern) rather than being read live every frame; unticking Instance Overridable removes the dispatchers too (asked; it used to keep them); a whole-button preset keeps neither the button's content nor its Button Tag / label widget; Design channels on an unfilled Shape Style go to the brush, decided by the style as authored (not per state).
- **Still open:** deleting an Instance Overridable button leaves its variable and dispatchers (untick first); placements' graphs bound to a renamed dispatcher in other Widget Blueprints rely on the engine's rename following them; a preset asset edited while a Widget Blueprint using it is open reaches it on its next load, not live; whole-button presets across kinds of buttons only carry the settings both kinds have; Design channels following a per-state Fill switch (they follow the style as authored, or a state's own style's Fill); a placement's instance overrides can't change a state's Shape Style; the brush inside an unfilled style is stretched across the shape's box (a Box / Border brush's margins aren't kept) and takes no Disabled draw effect.

## Ready-made buttons (`Buttons/Widgets/`, palette "NameTBD Buttons")
- `UStyledButtonBase` (abstract, `StyledButtons.h`; `PrioritizeCategories = "Style"`): a ready-made button is **parts** + **Style**.
  - **Parts** (hidden from the Hierarchy in the button's own tree - see below; `BuildParts`, once, when placed - see Palette drops - or at runtime when built empty): widgets made in the button's WidgetTree (`MakePart`, plain name while free; `MakeLabel`, `Sized` = a part in a named Size Box, `SetButtonContent`). Each is remembered by role in `PartNames` (role -> widget name: Label, Knob, KnobBox...) and found again with `FindPart` (marks it modified, for the style's undo) / `GetPart` (unmarked, runtime). `BuildDefaultContent` is `final`: resets the targets and `PartNames`, then `BuildParts` + `ApplyStyle`.
  - **Style** (category "Style", top of the Details): `bUseStyle`, `Motion` (`EStyledButtonMotion` Smooth/Snappy/Bouncy/Gentle/Instant -> every target's speed/curve/overshoot), **`EnterDuration` / `ExitDuration`** right after it (seconds, hidden for Instant; 0 = Motion's pace, the old behaviour): the way in (hovered, pressed, on, chosen) and back out (to Normal). Shape speed = 1 / duration, Design speed = 3 / duration (it eases toward its goal); set either and every target gets its own Exit Interpolation Speed (Motion's speed for the side left at 0). Segmented Choice's slide follows Enter Duration. `GetShapeSpeed` / `GetDesignSpeed`. Then `AccentColor`, plus each button's own few settings (sizes, corners via `EStyledButtonCorners` Pill/Rounded/Square, colors). `ApplyStyle` (virtual) starts with `BeginStyle` (empties Shape/Design Targets and `LookBaselines`) and makes them all again from the Style settings, plus the Background Shape/Look (`MakeBackground<T>`, `SetCorners`), the content slot's padding/alignment (`SetContentLayout`, listed or hidden) and the parts' style-owned settings. Runs after `BuildParts`, and in `PostEditChangeProperty` when any property whose Category starts with "Style" changes (before Super, so the Context Menu Button lays the new Looks out). Runtime: set the properties, call `RefreshStyle`. **Changing a Style setting rewrites the targets and the parts' styled settings**; Use Style off keeps hand edits (and hides the Style settings).
  - Helpers: `MakeLook<T>` (a Look from a scratch copy of a shape), `AddShapeTarget` (motion-based) / `OverrideShape`, `AddDesignTarget` / `OverrideDesign` / `AddTint`, `AddDisabledFade`, `Lighter`. Label: `SetLabel` / `GetLabel` (Button Text Widget). Theme defaults in `StyledButtonTheme.h`. All: Should Destroy Card off.
  - **Hidden parts (fix9):** a ready-made button's parts are **not in the Widget Blueprint's tree at all** while hidden: they live in `UPROPERTY(Instanced) UWidgetTree* PartsTree`, a widget tree **owned by the button** (outer chain: part -> PartsTree -> button -> WBP tree), the way a User Widget keeps its widgets; the content slot sits in `UPROPERTY(Instanced) HiddenContentSlot` instead of `Slots` (`PartsTree->RootWidget` = the content). The Hierarchy lists nothing under the button; the compiler skips them (it counts only widgets whose nearest `UWidgetTree` is the blueprint's - see GUID rule), so they need no GUIDs; duplicate / copy / paste / undo carry them as the button's subobjects. Built (`RebuildWidget` builds `GetPartsSlot()`), drawn, released, targeted (`Gather` walks `GetHiddenContent()`) exactly as when listed. `ArePartsHidden()` = hidden content inside `PartsTree`.
    - `UContextMenuButton::SetPartsHidden(bHide, OutMoved)` (editor): moves the content and everything inside it (`UWidgetTree::ForWidgetAndChildren`) between the blueprint's tree and `PartsTree` by `Rename` - the same objects, so edits survive; a name taken where they go becomes `Name_N` (targets still find it: `FindWidgetInButtonTree` matches by stem). Hide = content slot from `Slots` to `HiddenContentSlot`; Show = back.
    - **Show Parts In Hierarchy / Hide Parts From Hierarchy** (top of Style, `FContextMenuButtonDetails` -> `StyledButtonsEditor::ToggleParts`): on the **Widget Blueprint's own copy** (found by name from the preview copy), one transaction (blueprint modified, GUIDs synced inside it), then structurally modified. Hidden parts can't be Blueprint variables or Sequencer targets (tooltip says so).
    - A fresh build hides the parts (`BuildPendingInBlueprint`); `bPartsVisibilityDecided` (editor-only UPROPERTY) marks the choice made. Ready-made buttons from before fix9 (listed parts) are hidden **once**, outside any transaction (an upgrade, not an undoable edit).
    - The designer doesn't mark widgets of the button's own tree as being designed: `RebuildWidget` passes the button's `GetDesignerFlags()` to them (editor only). Their `GetWorld()` is null (UWidgetTree's world comes from a User Widget outer) - fine for the ready-made parts (text, images, shapes, boxes); a widget needing a world shouldn't be added to hidden parts (show them).
  - **Legacy hidden parts (fix6-fix7):** those kept the parts in `HiddenContentSlot` with the widgets still in the blueprint's tree - which the editor/compiler/duplication code doesn't expect (the template ended up pointing at the compiled class's trashed widgets, `TRASH_Check_0`). `RestoreHiddenParts` (`PostLoad`, and `BuildPendingInBlueprint` for any button holding a hidden slot): parts inside `PartsTree` are the button's own and kept (links fixed); others are put back into `Slots` when they're the button's own (in its tree, not listed by another widget), else dropped and the button marked pending (rebuilt) - the case of a pasted copy whose slot still names the original's parts. **Never keep widgets of the blueprint's tree outside a panel's `Slots`.** fix8's folding (`bExpandedInDesigner`) is gone.
  - **GUID rule (fix8, the engine's):** the Widget Blueprint compiler (`WidgetBlueprintCompiler.cpp`, ensures at lines ~794/~828 in 5.7) checks `WidgetVariableNameToGuidMap` against every widget the blueprint's tree **owns** - `UWidgetBlueprint::ForEachSourceWidget`: every widget nested anywhere inside the tree whose `GetTypedOuter<UWidgetTree>()` is that tree, listed in the Hierarchy or not - both ways: each needs a GUID ("Widget [X] was added but did not get a GUID") and each GUID needs one ("Variable [X] was deleted but still has a GUID"). `StyledButtonsEditorPrivate::SyncGuids` makes the map match exactly (same rule; only blueprints holding a Context Menu Button) - run on the pre-compile hook, on `FCoreUObjectDelegates::OnAssetLoaded` for Widget Blueprints, after a sweep, inside the Show/Hide transaction, and right before every `MarkBlueprintAsStructurallyModified` made here (that call compiles synchronously, maybe without the pre-compile hook). Orphan parts must be swept out of the tree (renamed to the transient package), not left to garbage collection, or their GUIDs go stale between compiles: `SweepLeftoverParts` removes parts whose ready-made button left the tree, and parts a button that holds other content no longer holds (an empty button - an undone build - keeps everything for redo).
  - **Button preview toolbar (fix9, `NameTBDEditor/Private/ButtonPreviewToolbar.h/.cpp`):** in the Widget Blueprint editor's toolbar (`AssetEditor.WidgetBlueprintEditor.ToolBar`, own section, dynamic entry per editor - same pattern as the Widget Animation controls in `WidgetAnimBuilderToolbar.cpp`), collapsed unless one Context Menu Button is selected: `Name | Idle Hover Press On Disabled | < value > | Replay` (~400 px, ~520 with the stepper; On only when Button Can Be Enabled; the stepper only for a button with values). Acts on the selected **designer preview copy** only (nothing authored or saved). `FSelectedButtonPreview` remembers per button name what was picked and shows it again, at once, whenever the designer remakes its preview (`FWidgetBlueprintEditor::GetPreview()` changed); Replay plays the button's last change again from where it started.

## Materials on Context Menu Buttons
> **Standing expectation (the user's own words):** "There could be more use cases that users desire that I haven't thought of, but would be expected in a production-grade application."

- **Asked:** "Materials don't work on context menu buttons at all. They can be set, and even show in the editor, but in game they do nothing."
- **Why:** the designer shows the button as authored (preview None), the game shows its states. (1) A Shape Target's state Looks are whole copies of the Background Look made when they were laid out (the ready-made buttons make Hovered / Pressed / Enabled Looks with a flat fill); a material set on the Background Look's fill afterwards made `Fill` differ between the base and the Looks, so `GatherLookProperties` gave it to the states and every state painted its old flat colour over the material. (2) A Design Target's Material on a shape (Self with a Background Shape, or a shape part) was swapped in once per state change, then the same frame's Look blend (and any later `SyncBackgroundShape`) wrote the whole paint back, so the material vanished and its parameters went to an instance nobody drew.
- **Fix:**
  - `RepairLookImages` (on load and on every Background Look edit) and the same repair against each shape's authored look in `InitializeRuntimeShapeTargets`: a state Look's paint (fill, or a stroke's paint) that draws no image where the shape as authored draws one (a texture, material or SVG) takes the authored paint whole, so the image shows in every state.
  - **Background Look edits reach the states** (`PropagateBackgroundLookEdit`, editor): against `BackgroundLookSnapshot` (editor-only, the Background Look as last laid out), every value the edit changed goes into each Self state Look that still had the old value; a state's own changes stay. Structs holding structs or lists (paints, strokes) are followed member by member; gaining or losing an image changes a paint whole.
  - `ApplyDesignTarget` puts a Design Target's Material back when the widget no longer shows it (or an instance of it), and points its parameters at the instance actually drawn; the same for a Brush Texture / SVG on a shape.
  - A vector Background Shape whose fill or stroke draws a material (or any non-texture resource) marks the brush layer changed every paint, so it animates even if the layer keeps an offscreen drawing.
- **Beyond the request:** edits of any Background Look setting (rounding, stroke, gradients...) now follow into the states that didn't change them, not only images; SVG and texture fills are kept like materials; Design Target brush textures / SVGs on shapes are protected like materials.
- **Decisions made without asking:** a state that painted a flat colour over a later image takes the authored paint whole (image and its tint) rather than tinting the image with its old colour: the old hover colour of a dark surface would have turned the material near black. Hover / press feedback on such a button then comes from its other channels (transform, Design Target tint) until a state is given its own image.
- **Still open:** telling a state's deliberate flat colour over an image apart from a stale one in assets saved before this fix (both read the same); per-state tint of an image fill as a relative brightness (a hovered material a step lighter) instead of a replacement.
